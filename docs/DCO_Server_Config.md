# DCO AI server config reference

Generated from the DCO_AI source on 2026-10-11 05:40 UTC by the DCO Features Auditor (scratchpad gen_cfgdoc.js). Regenerate after code changes.

## How the file works
- File: `$profile:DCO/DCO_GlobalConfig.json` in the server -profile folder. The server reads it once at start. The log line `N settings overridden from $profile:DCO/DCO_GlobalConfig.json` shows how many keys were applied, and the `config ...` / per-category lines show the active values.
- With Auto Generate on, missing keys are added with the current value (the old file is copied to .bak first). Keys you remove come back at the next start; to drop a key permanently turn Auto Generate off.
- Shipped value = the value a fresh server writes into the file (auto-generated by DCO with the default world settings). Values outside the range are clamped.
- Keys starting with `tune_` are fine-tuning values. A value equal to the default means the built-in behaviour.
- Problems are logged in dco.log and the server keeps running:
  - `cfg_clamped`: a value is outside its range and was clamped;
  - `cfg_bad_type`: wrong type, e.g. "2" in quotes for a number or 12.5 for a whole number; that key keeps its previous value and the file is not rewritten;
  - `cfg_parse_fail`: the JSON is invalid; the file is not touched and the previous values stay;
  - `cfg_unused`: a key no code reads, usually a misspelling.
- A misspelled key is not kept: when the file is rewritten (missing keys added or Save to server config from GM), only real keys are written, so copy the correct name from this table.
- Whole numbers are fine for number keys: `"aiAggression": 2` and `2.0` both work (verified 2026-10-10).
- Defaults follow DCO updates. Next to the JSON, `DCO_GlobalConfig.defaults.<world>.txt` (one file per world/scenario) records the default of every key for that world at the last write, so rotating scenarios does not trigger migrations.
  - At start, a key whose JSON value still equals that old default takes the new default when the code default changed. This is logged as `cfg_default_migrated`; the file is rewritten and a `.bak` backup is kept.
  - Values you edited are never changed.
  - For a file from before this version, the first start only records the defaults and lists up to 40 values that differ from the current default (`cfg_differs_from_default`). It does not migrate them. Edit those keys by hand if they are frozen old defaults.
  - Do not edit the `.defaults.<world>.txt` files.
- The JSON is written readably, one key per line, with floats rounded to at most 6 decimals.

## Per-faction values
- Add a `"factions"` block to give one faction different values. Example:

```json
"factions": {
  "USSR": { "aiAggression": 1.5, "tune_agg_profile": 1 },
  "FIA": { "takeCoverChance": 0.5 }
}
```

- Any key from the tables below can be used inside a faction. The value applies to that faction only.
- Order of layers, last one wins:
  1. global values in this file;
  2. GM global settings;
  3. this file's faction block;
  4. GM faction settings.
- Ranges and clamping are the same as for the global key (logged as `cfg_clamped scope=<faction>`).
- A key that DCO does not know inside a faction block is logged as `cfg_faction_unknown_key`; applied values as `cfg_faction_applied`.
- Keys that only work server-wide are ignored inside a faction block and logged as `cfg_faction_global_only`: doctrine* keys, groupPreset* keys, `gmSaveConfig`, `startupPresetPrompt`, `perfProfiling`.
- Faction entries that are not objects, are empty, or name a faction that does not exist are skipped (`cfg_faction_skip reason=not_object / empty / unknown_faction`) and stay in the file.
- If `"factions"` itself is not an object (e.g. an array), it is logged as `cfg_factions_not_object`; the file is then not rewritten, and the GM save is refused, so nothing is lost.
- The block is kept when the file is rewritten (missing keys added, default migration, GM "Save to server config"). A GM save writes the block as it was when the server started, so edit the block only while the server is stopped.
- A GM save is refused while the file has a JSON error (`cfg_save_gm result=skip reason=parse_fail`), so a broken admin file is never overwritten.
- `gmSaveConfig` (gm / admin / off) controls who may press "Save to server config" in the GM Presets window. Saving writes all current values, including defaults, into this file.
- GM name = the same setting in the Game Master DCO Settings window. GM changes apply live but are not written back to the file. Per-faction GM overrides start from this file's values.

## Interaction with aiAggression (read this before tuning soldier settings)
- Effective aggression = `aiAggression` x 2.5 (shipped 1 -> 2.5).
- `takeCoverChance`, `dodgeChance` and `suppressionEffect` are multiplied by 1 / effective aggression when it is above 1 (shipped: x 0.4), or by (2 - effective aggression) below 1. Example: shipped takeCoverChance 0.8 -> a soldier uses 0.32. They still change behaviour across their whole range.
- `grenadeUsage` and `glUsage` are multiplied by effective aggression and capped at 1. At the shipped aggression every value from 0.4 to 1.0 gives the same result (maximum use). Only values below 0.4 make a difference until this is changed (reported 2026-10-10).
- Squad pull-back thresholds (casualties before stepping down / going evasive) also scale with aggression; at the shipped value squads almost never pull back on casualties alone.

## Verified in game
- `aiAggression` (verified 2026-10-10, PERF_STRESS, about 170 AI, JSON values 0.5 / 1 / 3, one run each): first kill at 189 / 176 / 127 s, panic flights 53 / 18 / 2, groups switching to EVASIVE 32 / 18 / 18, deaths while pinned 37 / 14 / 14, movement orders 245 / 305 / 565, close-quarters engagements 231 / 226 / 414, fratricide 8 / 3 / 3. Low = careful and easily shaken, high = pushes in fast and rarely panics. Above 1 the squad posture choice no longer changes; soldier-level effects keep growing.
- Config arms (verified 2026-10-11, PERF_STRESS, about 170 AI, no commander, one run per value, compared with the mean of 3 default runs of the same build; indicative only):
  - `suppressionEffect` 0.2 (default 1.0): panic flights 1 vs 23, deaths while panicking 0 vs 17, deaths in the open 54 vs 69, total deaths 65 vs 74, first death at 132 s vs 110 s. Lower values make soldiers much harder to pin down and panic.
  - `takeCoverChance` 0.2 (default 0.8): total deaths 76 vs 74, first death at 83 s vs 110 s, median kill distance 18 m vs 15 m. A small effect at the default aggression.
  - `superiorRatio` 1.0 (default 2.0): deaths 75 vs 74, kills 71 vs 67. No clear effect in a test without commanders; it mainly changes when commanders and groups decide to attack.
  - `tune_spec_assist_commit_s` 0 vs the default 6 (3 runs each): with 0, friendly-fire deaths 10.3 vs 6.7 per run and machine-gun assistants switch targets more often (31% vs 17%). Keep the default.

- Functional checks (2026-10-11, 300 s, PERF_STRESS on a base world with the server config ON; each run changes one key; the value was confirmed in the log):
  - `overmatchAssault` false: works. Overmatch assaults 0, against 5 in the runs with true.
  - `superiorRatio` 4: works. The overmatch threshold used doubles (need=3.6 against 1.8 at ratio 2). The number of overmatch assaults stayed at 5, because the real force ratios in this test were far above both thresholds.
  - `suppressionEffect` 2: works. Panic lines 36 against 14-18 at 1.0, with no rise in deaths.
